# Account deletion: tracked requests and manual cleanup

The app provides authenticated tracked deletion requests with server-acknowledged references, plus an email fallback. Status tracking is not automated deletion. It never calls `deleteUser` alone, never deletes Firestore from the client, and never reports completion on opening email. Email delivery/monitoring and identity verification are not established by code. This is a launch blocker until an operationally supported, owner-approved process is verified.

## Why Auth-only deletion is unsafe

Owned records span `users/{uid}`, `providers` (`ownerId`), immutable `serviceRequests` (`ownerId`, with complete proposed personal data), retained `requestSlots` (`ownerId`), `archivedProviders` (`ownerId`, including retained contact snapshots), `supportRequests` (`ownerId`, including deletion requests), `serviceQuotas/{uid}`, request schedule-validation child receipts, and potentially `reports` (`reporterId`). Reports by other users can reference owned services. Auth deletion is not a cascade. Current rules forbid profile/request/slot deletion from normal clients; administrative request/slot history is also retained. A trusted cleanup mechanism with explicit authorization is required. No rules were weakened or deployed in this task.

## Required workflow before enabling deletion

1. Owner approves retention classes, support response time, public listing removal and identity verification. Do not accept an arbitrary UID or unverified email as authorization. For self-service, require current authenticated identity and recent reauthentication with the original provider (Email/Password or Google); handle `auth/requires-recent-login` without collecting passwords in Firestore/support emails.
2. Implement a trusted backend or operator-only administrative tool outside the mobile bundle. Use least-privilege access, dry-run inventory, pagination and durable operation checkpoints. Never put service-account credentials in the app. Cloud Functions would require a separately approved deployment/billing decision; none was added here.
3. Freeze new writes for the target identity during cleanup with a tested server/rules mechanism. Merely disabling Auth/revoking refresh tokens does not instantly invalidate already issued ID tokens in Firestore. Current rules have no deletion-lock check. Account for in-flight submissions and admin reviews before cleanup; this is an explicit missing dependency.
4. Inventory only the verified target's owned records, including all pages and history, not just the app's 100-result queries. Hide/remove public `providers` first. Include unpublished/restored archives, all support/deletion tickets and notes, and `serviceRequests/{id}/scheduleValidation` child receipts. Firestore parent deletion does not delete subcollections. Delete/anonymize the private profile, all owned request proposals/review PII and slot metadata according to the approved schedule. Handle own reporter identity and references in others' reports narrowly; do not delete another user's report merely because it references a service. Retain only specifically justified minimum data with a confirmed expiry/access policy.
5. Verify no target-owned public/provider/private PII remains unexpectedly accessible, then delete the Auth account through the trusted mechanism. Clear local drafts and the session on devices when they next observe session loss; the mobile auth observer also attempts this cleanup. Public favorites are device-local and independent of accounts. Remote deletion cannot wipe an offline device immediately. After confirmed completion, and verify the account cannot sign in again. Do not tell the user everything was erased before the cleanup is verified.
6. If cleanup fails, keep the operation checkpoint and identity lock, report pending status, retry only the unfinished idempotent steps and verify again. If Auth is already gone, use the stored verified UID/checkpoint to finish cleanup; never recreate a dummy account. Never log passwords, full numbers or unrestricted payloads.

This is a design/runbook for review, not an installed endpoint. No production identity or data was deleted. Tests cover confirmation, cancellation, email failure and truthful status; they do not claim server deletion or reauthentication integration exists.

## Tracked-request operations

The app stores private support/deletion tickets and staff-visible-to-user notes. Deletion states are received → in_review → awaiting_verification → ready_for_deletion, or rejected with an explanation. `ready_for_deletion` means ready for an authorized operator; it never means deleted. Owners cannot change status. Preserve a separately secured operator checkpoint before removing the ticket/account so a partial cleanup can resume without recreating Auth.

After verified manual cleanup, send the final completion receipt manually by email: account-based ticket tracking will no longer be accessible. Keep only retention-approved minimal audit information with a defined expiry; do not retain unrestricted ticket/proposal PII by default. Verify inbox monitoring, identity verification and operator access before release. The app does not implement a deletion-lock backend, deletion worker, notification service, or automatic email completion.
